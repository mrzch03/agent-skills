# product-design-review — 像水龙头一样的产品交互

## 从用户手上有什么开始

先写清：谁在操作、手上有什么、它在哪里、想完成什么、什么可观察结果算完成。默认操作者首次使用、不熟悉内部术语。列出完成任务需要作出的决定，能由系统可靠推导的值自动带入，并允许检查。

“现代交互”要落实成具体动作。截图在剪贴板，就应能在相关输入区粘贴；图片在文件夹，就应能拖入或选择。结合产品支持的平台选择入口，让用户直接使用已有材料，减少另存、转格式、查编号和跨页搬运。只写“支持上传”不足以表达这些要求。

## 像水龙头一样操作

水龙头的价值在于：看得懂怎么开，转动就有水，调节能感到变化，关上就能停。将控制、反馈和结果连接起来，用户无需先理解内部管道。

- **动手前能预料结果。** 用熟悉的名称和控件说明操作对象、影响范围和生效时机。预览与控制尽量靠近；复杂参数按需展开。
- **动手时知道系统接住了。** 按压、选中、拖动当下有反馈。异步操作立刻显示正在做什么，并防止重复提交；确有依据才显示进度或剩余时间。
- **调节后能感到对应变化。** 可实时生效的配置就地预览；有延迟、需保存或发布的配置明确说明边界。区分保存、发布、受理、排队、实际执行和结果未知。
- **停止和恢复容易找到。** 持续操作有可达的停止入口；可逆操作尽量一步完成，支持撤销或恢复。高影响操作说明后果，确认默认落在安全选项。
- **动效解释变化。** 用短而一致的动效说明对象、位置或状态的变化，避免挪动操作目标。尊重减少动效设置，文字和静态状态仍能表达结果。

## 设计判据

| 原则 | 设计与走查时要回答的问题 |
| --- | --- |
| 结构清楚 | 用户能说出每个模块做什么、彼此怎么关联、现在该去哪一步吗？按用户任务组织页面，避免直接把后端模块搬成菜单。 |
| 同层集中 | 相同作用范围和生效时机的配置能在一个地方完成吗？引用资源时能就地查看、选用，再回到原编辑位置吗？ |
| 看得见、选得出 | 优先提供名称、预览和可选项，减少记忆和手填编号。内部 ID、协议、原始错误放入适当的诊断详情。 |
| 配置可验证 | 正式执行前能试一次，看见或听见对应效果吗？预演说明使用的版本、验证范围和仍未验证的部分。 |
| 关系和优先级可见 | 当前执行什么、谁在等待、谁被阻止、原因与下一步是什么？复杂关联用依赖图、队列或时间轴呈现，依据实际判定。 |
| 反馈就在操作附近 | 用户无需到日志里猜结果；按钮、对象和结果区域表达一致的状态。成功后能找到实际产物，并继续下一步。 |
| 防错且能恢复 | 空状态、禁用、失败、过期各有可执行的下一步。失败保留可恢复输入；结果未知先核对原操作，避免重复执行或计费。 |
| 上下文有归属 | 同一任务内返回保留合理的筛选、草稿和进度；换账号、工作区或对象时隔离对应状态，恢复依据已确认的归属。 |
| 一致且人人可用 | 沿用产品的视觉语言、组件和术语；关键任务支持键盘，焦点可见且开关弹窗后位置合理，状态不能只靠颜色。 |

## 把原则变成验收场景

按本次功能选择相关场景，每项写下“起点 → 动作 → 可观察结果”，覆盖主流程及关键恢复路径。

| 场景 | 验收关注点 |
| --- | --- |
| 剪贴板有截图、文件夹有图片 | 粘贴、拖入、选择共用校验；本地预览可替换或取消。需要确认才入库的流程，确认前不上传。失败保留输入，重试范围清楚。 |
| 点下操作后服务响应慢 | 当下有反馈，等待时不提前提示失败或核对；防重复提交。收到受理回执不能冒充实际完成。 |
| 上传后仍处于其他类型筛选 | 用户立即找得到新产物；可以转到对应类型，或解释被筛选隐藏并提供直达入口。分页筛选要说明覆盖范围。 |
| 操作中登录失效 | 明确当前操作是否发生、输入如何保留；能从当前位置恢复验证，再回到原任务。身份未确认时不沿用旧身份权限。 |
| 账号 A → B → 返回 A，或刷新页面 | B 不显示或操作 A 的私有内容；回到 A 按归属恢复未完成事项。清理遗留记录不误清当前有效任务。 |
| 结束、删除或取消 | 确认文案说清对象、影响和不可逆部分；取消不产生副作用，确认只执行一次，结果可核对。 |
| 同时触发互斥任务 | 展示实际执行、等待或受阻及原因，提供可用下一步；可修改的规则有明确入口和生效范围。 |

## 优化顺序与边界

1. 先处理挡住主任务、串用上下文、误操作和错误宣称成功的问题，再处理反复搬运、恢复困难，最后打磨视觉细节。
2. 先补全操作的开始、等待、完成、失败、恢复，再优化装饰。保留已有设计语言，架构升级时重新审视流程，不机械照搬旧实现。
3. 工程术语改成中文仍可能要求用户理解工程概念。“输入编号”改名不等于完成选择器；缺少查询、状态或身份能力时，列明依赖，按项目协议补齐。
4. 页面状态只能依据真实可观测信息。没有播放回报就不能显示正在播放，没有全库查询就不能声称全库搜索；明确已完成与待补齐的能力。
5. 通用经验留在本 skill；项目页面清单、接口约束、具体问题和验证结果留在项目文档。开发规范按需读 [dev-standards](../dev-standards/SKILL.md)。

## 走查与复验

1. 画出本次用户任务经过的页面和对象，检查每个模块的职责、配置归属与跨页交接。审查范围由用户任务决定。
2. 用实际页面走相关验收场景，记录卡点、用户影响、证据、修改方向和复验动作；首次使用、空状态、失败与恢复不能只看静态截图。
3. 按“通过 / 部分通过 / 未通过 / 待验证”记录结论。区分观测到的问题、源码推断和设计建议，不把建议写成已有能力。
4. 改后用相同任务和样本复验。单测验证状态规则，浏览器或应用实操验证组件组合、焦点、切页、等待、重复操作与恢复。账号切换时也检查旧页面或弹窗是否残留。
5. 在支持的窗口尺寸、键盘操作和减少动效设置下检查关键任务。不要把直接修改页面状态当成真实用户操作；模拟输入需标注范围。
6. 汇报改动、证据与剩余缺口。模拟接口不等于真实服务，浏览器剪贴板事件不等于操作系统复制粘贴；真实服务、付费或发布按现有授权执行。

验收时让首次使用的人能回答：**我在操作什么？这一步会发生什么？刚才发生了什么？接下来能做什么？**
