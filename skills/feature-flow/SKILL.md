# feature-flow — 按风险开发功能

采用 [开发流程的分级](../dev-standards/dev-flow.md)，通用约束见 [dev-standards](../dev-standards/SKILL.md)。本流程编排工作，不另设项目分支、部署方式或授权。

## 1. 明确任务与验收

- 从用户目标判断需求是否合理、是否是上游设计缺陷、是否能用更简单的方式达成。需要改变目标或范围时说明取舍，不能自行替用户改需求。
- 写清操作者、起点、完成结果、范围及非目标；已有明确要求不反复确认。
- 涉及界面时用 [product-design-review](../product-design-review/SKILL.md) 定义主路径、反馈、失败恢复和上下文切换。
- **实现前形成验收场景与测试计划**：入口、输入、预期结果和证据点。计划随发现更新，不等代码评审结束才想怎么测。

## 2. 记录任务、设计方案

用 [issue-branch](../issue-branch/SKILL.md) 关联已有任务或建立必要记录，遵循项目的分支规则。
按 [方案模板](references/tech-design-template.md) 选择相关项；标准功能可直接写在任务记录中，高风险变更展开关键假设、兼容、失败处置和发布措施。
跨边界先明确合同、归属和消费者；数据变更按实际引擎使用 [数据库规范](../dev-standards/db-conventions.md)。

## 3. 按影响评审方案

按 [评审清单](references/design-review-rubric.md) 检查可行性和验收设计。标准功能保留简要设计自检；关键不确定性先做最小验证。
高风险变更在依赖该假设的实现或发布之前，由项目指定负责人核对相关风险；独立技术 reviewer 可检查方案，但不能代替用户或负责人决定业务取舍、费用与发布授权。
不固定要求三个人、三份文档或字母评分。项目已有审批要求则遵守。尚未解决的阻塞项明确标明阻止哪一步，其余独立工作可继续。

## 4. 实现与测试同步

按可交付单元实现，必要单测、合同测试和集成检查同步完成。性能或并发变化使用能暴露对应问题的样本。并行任务遵循 dev-flow 的边界、共享合同和集成顺序。

## 5. 独立评审与复验

用 [codex-review](../codex-review/SKILL.md) 提供需求、设计、准确的差异范围和已有测试证据。修复发现的问题，复验受影响部分；评审批准不替代必需测试。
用 [verify](../verify/SKILL.md) 操作完整链路；前端检查实际交互，跨模块检查组合行为。真实服务暂不可用时，保留模拟验证的价值，同时明确尚未通过的验收项。

## 6. 集成与交付

按项目规则提交、推送和 PR/MR，验证最终候选版本；发布仅在授权范围内执行。记录各阶段的真实状态，任务关闭依据验收范围，不能因代码合入就自动宣称上线或真实联调完成。
