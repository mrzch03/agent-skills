# 数据库与 Redis 开发规范

先确认实际引擎、版本、环境、数据规模、访问频率和项目限制。此文是通用原则；具体判读按下面的专项文件，不将某项目的容量阈值或语法限制泛化。

## 正确性先于优化

- 明确一致性、并发竞争、幂等、租户隔离和事务边界；锁与事务依据业务不变量设计，不为减少 SQL 数量牺牲正确性。
- 分页需要稳定顺序；批处理有可恢复进度和明确边界。数量上限按容量和延迟预算验证，不统一规定行数。
- 不机械把 JOIN、子查询、反条件改成多次查询；比较语义、往返、扫描成本及事务窗口。`COUNT(*)` 与 `COUNT(column)` 的空值语义不同，不盲目互换。
- 新增或改动数据访问时记录操作对象、触发频率、预期返回/扫描规模和性能影响，写在任务或项目指定审计位置。

## 需要哪些性能证据

- 热路径、大数据集、复杂连接、批量写入、索引或查询形态变化：使用代表性参数和数据分布查看执行计划，必要时在隔离环境实测延迟、锁等待及资源成本。
- 小表或简单有界点查：说明规模与访问路径，并做相关测试；项目要求每条 SQL 提供计划时从其规定。
- 计划中的行数通常是估算；区分估算与实际结果。扫描类型、低基数或索引命中都不能单独证明性能好坏。
- 缺少代表性环境时记录限制，不能用小样本声称生产通过。高风险性能假设未验证时，不放行依赖该假设的发布。
- `EXPLAIN ANALYZE` 会执行语句；先检查对应引擎语义，在允许的隔离环境操作，写入、锁、函数副作用不因“分析”而获得授权。
