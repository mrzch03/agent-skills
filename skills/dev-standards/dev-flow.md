# 开发流程

## 先确认项目约定

读取项目 AGENTS.md、相关合同、任务记录、handoff 和当前 Git 状态。确认改动基线、允许的合并方向、检查命令、环境及已获授权。不擅自覆盖未提交工作，不为遵循通用模板改变项目架构或分支模型。

分支来源以项目规定和当前任务上下文为准；有本地未推送依赖时明确记录，不一律从远端重建。更新共享基线、发布、生产操作按现有授权处理；只有缺失的决定确实阻塞时才提问。

## 按风险选择流程（分级的唯一规则）

| 等级 | 判定 | 所需证据与流程 |
| --- | --- | --- |
| 小改 | 范围清楚、影响局部、容易恢复，无跨边界行为或数据兼容性变化 | 简述目标与验收；实现、针对性验证和差异自检。走 [hotfix-flow](../hotfix-flow/SKILL.md) 的小改路径 |
| 标准功能 | 新增用户能力、局部接口或多组件协作，依赖和失败路径可界定 | 用户场景、简要方案、开发同步测试、独立评审、相关链路验证。走 [feature-flow](../feature-flow/SKILL.md) |
| 高风险 | 涉及权限或租户隔离、计费、不可逆数据变更、资源生命周期、破坏兼容或大范围故障影响 | 在标准流程上补关键假设验证、迁移兼容矩阵、故障恢复与发布措施；适用项由相关负责人确认后执行 |

按实际影响判断；改一行也可能高风险，有接口变更也不一定需要完整架构重设计。开发中发现风险扩大，重新分级并补上对应检查。
**紧急程度与风险分开**：紧急修复仍需风险分级；特殊时序见 hotfix-flow，不默认省掉权限和核心正确性检查。

## 通用顺序

1. 明确用户任务、范围和可观察验收结果；涉及界面时先用 [product-design-review](../product-design-review/SKILL.md)。
2. 在项目选定的任务记录中写计划和测试场景；按风险补方案，协议变化先定合同。
3. 实现一个可交付单元，同时编写有意义的测试并运行相关检查。
4. 标准功能与高风险变更用 [codex-review](../codex-review/SKILL.md) 独立评审，提供改动及已有验证证据。修复发现的问题后复验受影响部分。
5. 按 [verify](../verify/SKILL.md) 完成相关链路验收。按项目规则提交 PR/MR；缺少必需证据时明确阻止对应的合并或发布，不伪报通过。
6. 合入前核对最终候选版本；基线更新或冲突解决改变行为时，在合并结果上跑相关检查。部署后核对目标版本及实际健康状态。
7. 更新任务与交接；项目需要 CHANGELOG 时按其格式记录，不强制每个小改新增一份流水账。

## 并行任务与 worktree

- 仅在任务授权或适用流程要求委派时开启并行代理；先识别依赖，串行的事情不伪装成并行。
- 每个任务写清目标、文件/模块边界、基线、输入输出合同和验收；指定集成人。共享协议先稳定，由明确的负责人维护。
- 独立任务可使用独立分支和 worktree，避免同时改共享文件。记录依赖提交与合入顺序；不把未完成的其他任务混进评审。
- 优先在任务 worktree 中构建和测试。环境只能在共享目录运行时，使用隔离候选版本或串行验证，不先合入未验证代码来迁就工具。
- 集成人检查各任务 diff 和证据，按依赖顺序集成，再验证组合后的行为；各自测试通过不代表集成通过。
- 同步基线可用项目允许的 merge 或 rebase；不改写他人的共享历史。冲突在候选分支或隔离 worktree 解决并验证，再按项目流程合入。
- 清理 worktree/分支前确认工作已保存、需要的提交已保留且无人使用；不强制删除含未提交工作或独有提交的目录与分支。

## 完成状态分别记录

实现完成、本地检查通过、独立评审通过、真实服务验证通过、已合入、已部署分别记录版本与证据，不用一个“完成”替代。不是每个任务都要求部署；按任务验收范围收尾，范围外待验证项明确列出。
