# hotfix-flow — 小改与紧急修复

先按 [dev-flow](../dev-standards/dev-flow.md) 判断风险，工程约束见 [dev-standards](../dev-standards/SKILL.md)。

## 普通小改

1. 一句话说明目标、影响范围和验收结果；修 bug 时先定位根因。
2. 关联已有任务；是否新建 issue、分支命名按 [issue-branch](../issue-branch/SKILL.md) 和项目规定，不为一次文案调整强制新建整套文档。
3. 完成改动并自检差异，运行相关检查。测试用于验证实际行为，纯文案/文档调整可用内容、链接、格式或页面检查。
4. 按 [verify](../verify/SKILL.md) 留下与改动相称的证据；项目要求独立评审时执行，发现跨模块或高风险影响则升级到 [feature-flow](../feature-flow/SKILL.md)。
5. 推送、PR/MR、合并与发布分别按当前任务授权执行；未要求部署时不自动发布。

## 紧急修复

1. 明确故障影响、当前环境和需要恢复的行为。优先评估已验证的回退、关闭开关等止损方式。
2. 紧急程度不降低风险等级。说明拟采取的操作、验证范围、回退条件与授权；已有授权直接使用，缺失的关键权限不靠“紧急”推断。
3. 控制修改范围，先做能保护核心正确性的检查；不顺带大范围重构。
4. 常规评审或验证确需延期时，必须符合项目应急规则并有授权，记录延期原因、剩余风险、责任人及补验期限。没有这些条件就不能自行先合后审。
5. 执行后观察真实恢复结果和回退触发条件；补齐原风险等级要求的评审与验证，登记后续根因修复。
