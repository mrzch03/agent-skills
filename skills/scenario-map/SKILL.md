# scenario-map — 能力总入口

拿到任务先读项目约定，确认目标、环境与授权，再按 [dev-flow](../dev-standards/dev-flow.md) 分级并选择 skill。各 skill 高内聚、用完即丢;知识一份一个家,别跨 skill 重抄。

## skill 的职责分层

| 层 | 放什么 | 有无状态 |
|---|---|---|
| **路由** | 本 skill:场景→skill 一张表,唯一入口 | 无 |
| **工序元事实**(怎么干活) | dev-standards / feature-flow / hotfix-flow / issue-branch / codex-review / verify / product-design-review——跨项目慢变规范 | 无,**永远不该有 handoff/进度** |
| **平台元事实**(系统是什么) | 各平台知识库 skill(权限与凭据获取方式/表结构/日志/历史 case，不存凭据本身) | 无 |
| **项目/场景**(在飞的事) | 项目认知 skill(用 project-skill-blueprint 建):元事实+handoff+项目任务记录指针 | 有,项目结束整包归档 |

通用 skill 允许项目特化版(如 GitLab 强制版 issue 流程):**特化版放项目工作区、不放全局**,文件头注明"特化自库版 <name>",避免同场景两个 skill 全局抢触发。

## 核心原则(动手前过一遍,所有场景通用)
- **第一性原理审题,优雅方案直击本质**:很多"问题"是上游设计缺陷的症状——修设计让问题**蒸发** > 技术上"解决"。新问题按序自问:①是不是上个补丁的债 ②需求本身合理吗(需求是输入不是圣旨,带来不成比例复杂度的要挑战)③是不是设计缺陷的症状 ④能不能删掉一个东西让问题不存在 ⑤确需新增,用最简模型卡它。
- **删机制优于加机制**;**简洁链路 / 行业标准 / 按实际边界抽象/ 以少为多**。
- 排障先核对实际环境配置与访问目标，不单凭账号或种子数据推断环境。**容量报错先问"这字段本该存吗"**(存错 > 存不下)。
- 详细规范(流程/提交/DB·Redis/协作)→ **dev-standards** skill。

## 路由表(场景 → 用哪个 skill)— 模板

> 通用路由保留在本仓。项目补充写到项目 AGENTS.md 或项目入口，不修改共享软链里的路由。

**本仓自带(固定):**
| 你要干什么 | 去哪个 skill |
|---|---|
| **标准功能 / 高风险变更** | `feature-flow`（用户验收、方案、开发同步测试、独立评审、集成验证） |
| **局部小改 / 紧急修复** | `hotfix-flow`（两条路径，紧急不降低风险等级） |
| **开发规范**(设计原则/流程/提交/DB·Redis/协作) | `dev-standards`(被所有场景 skill 引用) |
| 关联任务 / 建分支 / 提 PR·MR | `issue-branch` |
| 独立评审本地分支("走流程") | `codex-review` |
| 跑应用验证 / 自测出证据 | `verify` |
| 产品交互设计 / UI·UE 走查 / 页面流程优化 | `product-design-review`（任务起点→直接操作→反馈恢复→完整场景验收） |
| 给某项目/业务场景建一个"认知 skill" | `project-skill-blueprint` |

**项目专属（在项目入口登记实际位置）:**
| 你要干什么 | 去哪个 skill |
|---|---|
| **排查线上问题**(查库/日志/延迟/历史 case) | `<你的排查/知识库 skill>` |
| **某业务领域的活**(该领域全链路 playbook) | `<你的项目认知 skill;用 project-skill-blueprint 建>` |

## 维护
- **新增业务场景 skill 时,在本路由表加一行**(场景 → skill + 一句话)。
- 场景 skill 只放本场景 playbook + 引用 dev-standards;通用规范别下沉到场景 skill。
- 交接只属于有在飞任务的项目认知包；工序 skill 不记进度。按项目约定更新 handoff 指针，不依赖特定聊天命令。
